# Gemini: економія токенів і запитів

Правила для перекладів, рекомендацій, підбору за настроєм і вільного пошуку DropDate.
Додавання цього документа саме по собі не змінює поведінку API.

## Розрізняти два бюджети

- **Токени:** обсяг вхідних даних, відповіді та thinking. Менший корисний контекст і коротша відповідь знижують витрати.
- **Запити:** кількість генерацій за хвилину/добу. Навіть дуже коротка генерація витрачає запит.
- Ліміти залежать від проєкту й моделі. Їх потрібно читати з AI Studio та відповідей API, а не вважати поточне число універсальною константою. Додатковий ключ того самого проєкту не створює нову квоту. [Rate limits](https://aistudio.google.com/docs/rate-limits)

## Перед зверненням до моделі

1. Використати український текст TMDB або редакторське виправлення, якщо вони є.
2. Перевірити спільну БД за TMDB ID, типом медіа, мовою та вихідним текстом відповідного поля.
3. Формувати запит лише з полів, яких бракує або джерело яких змінилося. Готова назва не повинна повторно перекладатися разом з новим описом.
4. Якщо після перевірок роботи немає — повернути результат без Gemini.
5. Об'єднати однакові запити. Для кількох серверів потрібне спільне захоплення завдання з терміном дії; локального `singleflight` недостатньо.

Зміна моделі чи редакції промпту не повинна автоматично запускати повторний переклад усього каталогу. Масове оновлення — окреме контрольоване завдання.

## Компактний вхід без втрати змісту

- Використовувати окремі структури запитів для AI, а не серіалізувати повні відповіді TMDB чи фронтенду.
- Для перекладу передавати текст потрібних полів і мінімальний контекст для неоднозначних назв. Не передавати постери, посилання, рейтинги, акторський склад та вже готовий переклад.
- Для ранжування передавати ключ кандидата, назву, зміст і ознаки, які впливають на вибір. Обмежувати пул попереднім детермінованим відбором; не видаляти сюжет, коли він потрібен для розуміння теми.
- Прибирати дублікати, порожні необов'язкові поля та форматування JSON. Не скорочувати ключі до незрозумілих символів без виміряної користі.
- Відправляти релевантний зріз профілю смаку замість усієї історії користувача.
- Не обрізати вихідний опис для перекладу: розділити завдання за змістом або відкласти надто великий запис. Скорочений переклад не видавати за повний.

## Відповідь і thinking

- Для вибору питання достатньо `questionId`; для перестановки кандидатів — списку їхніх ключів. Не просити модель повторювати назви, описи чи вхідний JSON.
- Пояснення генерувати лише там, де вони відображаються в продукті, з конкретним обмеженням довжини.
- Використовувати JSON Schema; після відповіді перевіряти допустимі ID, кількість елементів, мову й відсутність вигаданих полів. Схема не гарантує фактичної правильності. [Structured outputs](https://aistudio.google.com/docs/structured-output)
- Вибирати `MaxOutputTokens` відповідно до кількості результатів і довжини тексту. Це стеля, а не гарантована витрата. Надто мала стеля може обірвати JSON і спричинити дорожчі повтори.
- Для простих перекладів і класифікації перевіряти мінімальне thinking, яке підтримує конкретна модель. Не переносити `ThinkingBudget: 0` на довільну модель без перевірки сумісності. [Thinking](https://aistudio.google.com/docs/thinking)
- Зберігати лише повні, перевірені результати. При обрізаній відповіді зменшувати пакет або коригувати бюджет, а не повторювати той самий невдалий запит у циклі.

## Пакети, кеш і черга

- Групувати незалежні переклади в одну генерацію за бюджетом тексту, а не тільки за кількістю фільмів. Використовувати стійкі ключі результатів і перевіряти відповідність джерелам.
- Першими обробляти відкритий тайтл і збережені фільми. Проміжні пошукові підказки та фонове поповнення каталогу мають нижчий пріоритет.
- Зберігати успішні поля одразу; при частковому оновленні не стирати готові поля. Повторювати лише незавершену роботу.
- Спільний облік у БД має охоплювати всі AI-функції та сервери. Резерв для інтерактивних дій не повинен витрачатися фоновими задачами.
- При `429` розрізняти короткий ліміт і добову квоту; поважати `RetryInfo`/`Retry-After`, якщо вони є. Перезапуск процесу не повинен скидати паузу після вичерпання квоти.
- Звичайний запит з масивом перекладів і **Google Batch API** — різні механізми. Batch API підходить для не термінової роботи, має окремі обмеження та цільовий час виконання до 24 годин. Перевіряти доступність і тарифи для обраної моделі. [Batch API](https://aistudio.google.com/docs/batch-api)
- **Кеш результатів у нашій БД** дозволяє взагалі не викликати модель. **Context caching Gemini** повторно використовує вхідний контекст; він не скасовує генерацію чи ліміт запитів. Не доповнювати короткі промпти зайвим текстом заради порога кешування. [Context caching](https://aistudio.google.com/docs/caching)

## Вимірювання й перевірки

Для кожної операції обліковувати модель, кількість елементів, звернення/влучання в кеш, вхідні, вихідні, thinking і cached tokens, тривалість, повтори й помилки квоти. Не додавати повні тексти, персональні профілі чи ключі в логи.

Використовувати фактичні лічильники з відповіді SDK. `CountTokens` корисний для калібрування типових пакетів і великих запитів; його не потрібно безумовно викликати перед кожною короткою генерацією. Оцінки за кількістю символів не є точним токенізатором, особливо для різних мов. [Token counting](https://aistudio.google.com/docs/tokens)

Порівнювати однаковий набір прикладів до/після: токени на успішно оброблений тайтл, кількість генерацій, обрізані відповіді, помилки зіставлення ID та якість української. Економія не повинна досягатися втратою змісту.

## Поточний стан і наступні зміни

**Уже є:** PostgreSQL для перекладів; пріоритет українського тексту TMDB; пакети назв до 50; компактний JSON; структуровані відповіді; обмеження пулу рекомендацій; часткове вимкнення thinking; локальний `singleflight`; тести з підставними перекладачами.

**Потребує реалізації або виправлення:** повторний переклад готової назви при перекладі опису; підтримка слоганів; спільна черга та добовий бюджет; пауза за фактичним часом скидання квоти; спільний облік токенів; розмір пакетів і вихідних бюджетів за обсягом роботи; перевірка thinking для всіх налаштованих моделей.

Цей список описує стан на момент додавання правил. При реалізації оновлювати його разом із кодом.
